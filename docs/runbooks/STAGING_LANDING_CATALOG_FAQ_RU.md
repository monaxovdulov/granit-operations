# Staging лендинга, каталога и RAG: FAQ для владельца

Статус: рабочая методичка для `preview.granitkr.ru`.

## Самое короткое объяснение

У staging есть два правила.

1. Лендинг выкладывается только из ветки `main` репозитория
   `landing-granit-static`.
2. Каталог на лендинге должен совпадать с копией каталога в backend.

Если вы поменяли текст, стили или обычную картинку, backend трогать не нужно.
Если вы поменяли карточки каталога, сначала надо обновить копию каталога в
backend, а потом выкладывать лендинг.

Production эта схема не меняет.

## Что означают основные слова

| Слово | Что это значит |
|---|---|
| `main` | Общая готовая версия лендинга. Только она может попасть на staging. |
| Рабочая ветка | Место для незаконченных правок. Она не перезаписывает staging. |
| Staging | Тестовый сайт `https://preview.granitkr.ru`. |
| Backend | Сервис на `https://manager.botops.ru`, к которому обращается widget. Там работают AI и копия каталога для поиска. |
| Индекс каталога | Файл `assets/catalog/catalog-index.v1.json` со всеми карточками, ссылками и версиями изображений. |
| Hash каталога | Отпечаток файла индекса. Одинаковый hash означает одинаковые данные. |
| RAG по каталогу | AI ищет варианты в закреплённой копии индекса внутри backend. Он не читает сайт заново при каждом сообщении. |
| SHA | Точный номер версии в Git. По нему можно понять, что именно сейчас работает. |
| Release gate | Проверка на сервере перед deploy. Она не даёт случайной ветке или несовместимому каталогу попасть на staging. |

## Я меняю только текст, цвета, блоки или CSS. Что делать?

Backend обновлять не надо, если индекс каталога остался прежним.

Можно написать Codex так:

> Закончи правки лендинга, проверь их в браузере, объедини с `main` и выложи на
> staging. Каталог я не менял. Production не трогай.

Что произойдёт:

1. Codex проверит, что индекс каталога не изменился.
2. Изменения попадут в `landing-granit-static/main`.
3. GitHub Actions попросит сервер выложить этот SHA.
4. Сервер сам скачает точные файлы из `main` и обновит preview.

Новая сборка backend для этого не нужна.

## Я меняю карточки каталога. Что считается изменением каталога?

Каталог изменился, если вы:

- добавили или удалили карточку;
- поменяли название, категорию, материал или описание;
- заменили изображение карточки;
- поменяли путь к изображению;
- изменили постоянный идентификатор карточки;
- перестроили разделы или фильтры, которые записаны в индекс.

Можно написать Codex так:

> Я закончил новую версию каталога в `landing-granit-static`. Синхронизируй
> индекс с `granit-operations`, сначала выложи совместимый backend на staging,
> потом объедини лендинг с `main` и выложи preview. Покажи мне оба SHA и hash
> каталога. Production не трогай.

Порядок важен. Сначала backend получает новую копию каталога. После этого
сервер разрешает deploy лендинга с тем же hash.

## Я хочу полностью переделать каталог

Если меняется только внешний вид страницы, а
`assets/catalog/catalog-index.v1.json` остаётся тем же, это обычное изменение
лендинга: backend обновлять не надо.

Если меняются сами карточки и данные, сначала скажите, должны ли старые ссылки
из widget продолжать открывать те же товары.

Если старые ссылки должны работать, постоянные `entity_id` надо сохранить.
Карточка может переехать в другой раздел или получить новое изображение, но её
идентификатор останется прежним.

Если старые ссылки можно сломать, это уже изменение контракта. Сформулируйте
это явно:

> Я разрешаю заменить структуру каталога и старые deep-link ссылки. Сделай
> миграцию каталога отдельной задачей, покажи список сломанных старых ссылок и
> план отката. Пока ничего не выкладывай.

Так большая переделка не смешается с обычным deploy.

## Я заменил изображения, но названия карточек не менял

Это всё равно изменение каталога. В индексе хранится `asset_revision`, который
зависит от байтов изображения. Благодаря ему браузер не показывает старую
картинку из кэша.

В release gate больше нет фиксированного списка разрешённых хешей отдельных
изображений. Проверка требует, чтобы файл открывался и его `asset_revision`
совпадал с индексом. Это позволяет менять изображения без переписывания gate.

## Я меняю только backend или логику AI

Новый commit лендинга не нужен, если его файлы и vendored widget не изменились.
После backend deploy надо повторно запустить landing workflow для текущего
`main`: он не меняет код сайта, но проверяет пару заново и обновляет
`release.json` с фактическим SHA backend.

Напишите:

> Выложи этот backend SHA на staging. Код лендинга и production не трогай.
> После deploy повторно запусти landing workflow для текущего `main`, проверь
> `/health`, `/release.json` и один бесплатный технический smoke без вызова
> модели.

Если для проверки нужен реальный платный вызов модели, Codex должен получить
отдельное разрешение.

## Я меняю сам widget

Widget хранится в лендинге как versioned artifact. Изменение backend не меняет
его JavaScript автоматически.

Нужен отдельный запрос:

> Собери новую версию widget, обнови vendored artifact в обеих страницах
> лендинга, проверь общий разговор между главной и каталогом, затем выложи на
> staging. Production не трогай.

## Я работаю в ветке и хочу посмотреть результат

Общий staging не принимает рабочие ветки. Это защита от ситуации, когда одна
сессия Codex затирает работу другой.

Для незаконченного варианта используйте локальный просмотр или отдельный
preview, который не связан с `preview.granitkr.ru`.

Если вариант готов, попросите Codex сначала аккуратно объединить его с `main`.

## У меня одновременно открыты две сессии Codex

Сессия, которая правит лендинг, работает в своей ветке и отвечает за
объединение результата с `landing-granit-static/main`. Сессия, которая правит
backend, не копирует файлы лендинга на сервер и не разворачивает свою старую
копию сайта.

После объединения с `main` лендинг выкладывает только его собственный workflow.
Сервер скачивает этот `main` сам. Поэтому backend-сессия физически не может
подменить каталог файлами из своего checkout.

Если обе сессии меняют каталог, не выкладывайте их независимо. Сначала выберите
одну готовую версию индекса, затем синхронизируйте с ней backend и только после
этого запускайте landing deploy.

## Как запустить deploy повторно

1. Откройте репозиторий `landing-granit-static` на GitHub.
2. Откройте вкладку `Actions`.
3. Выберите `Deploy static landing to preview`.
4. Нажмите `Run workflow`.
5. Оставьте ветку `main`.

Даже при ручном запуске сервер сам проверит текущий SHA `main` и hash каталога.

## GitHub Actions не запустился после push

Сначала проверьте, что commit действительно находится в `main`.

Если да, используйте ручной запуск из предыдущего раздела. Не надо повторно
переписывать файлы, создавать пустые commits или отправлять ветку напрямую на
сервер.

Если ручной запуск тоже не появился, попросите Codex проверить настройки
GitHub Actions. Сам серверный gate от этого отключать нельзя.

## Ошибка: deploy разрешён только для current main

Сервер получил SHA рабочей или устаревшей ветки.

Что делать:

- не обходить проверку;
- убедиться, что нужные изменения объединены с `main`;
- запустить workflow для `main` ещё раз.

## Ошибка: landing and operations catalog SHA-256 differ

Лендинг содержит одну версию каталога, а backend другую.

Что делать:

1. Остановить deploy лендинга.
2. Синхронизировать `catalog-index.v1.json` в `granit-operations`.
3. Выложить новый backend на staging.
4. Повторить deploy лендинга.

Не надо вручную менять hash в manifest или конфигурации. Hash считается из
самого файла.

## Ошибка: operations release metadata is unavailable

Backend не сообщил свой SHA или данные каталога. Обычно это значит, что backend
не запустился, работает старая версия или `/health` недоступен.

Сначала чинится backend. Лендинг в этот момент остаётся на прежней рабочей
версии.

## Ошибка: cannot build archive from landing main

Сервер не смог обновить свою read-only копию `main`. Причина обычно в доступе к
GitHub, сети или повреждённом Git-кэше на сервере.

Не отправляйте файлы на сервер вручную и не отключайте gate. Попросите Codex
проверить deploy key и переинициализировать server cache. Пока ошибка не
исправлена, preview остаётся на предыдущем release.

## Как понять, что сейчас стоит на staging

Откройте два адреса:

- `https://preview.granitkr.ru/release.json`;
- `https://manager.botops.ru/health`.

В первом файле видны SHA лендинга, SHA backend и hash каталога. Во втором видны
SHA работающего backend и hash его копии каталога.

Hash каталога должен совпадать. SHA backend в обоих ответах тоже должен
совпадать.

## Что Codex должен сообщить после deploy

- SHA лендинга;
- SHA реально работающего backend;
- версию и hash каталога;
- результат проверки preview в браузере;
- подтверждение, что production не менялся;
- что не было проверено;
- как откатить эту связку.

Фразы «всё готово» без этих данных недостаточно.

## Как откатывать staging

Если менялся только внешний вид лендинга, сделайте обычный revert-коммит в
`main`, который возвращает нужные файлы и не меняет индекс каталога. Gate
выложит новый SHA этого revert-коммита. Старый SHA напрямую он не примет.

Если менялся каталог, откатывается совместимая пара:

1. в рабочей ветке готовится revert-коммит лендинга со старым каталогом;
2. на staging возвращается backend с той же копией каталога;
3. revert-коммит становится текущим `main`, после чего запускается landing
   workflow.

Не делайте force-push и не передвигайте `main` на старый SHA.

Лучше попросить Codex так:

> Откати staging к последней совместимой паре через новые revert-коммиты, без
> force-push. Сначала покажи текущие и целевые SHA и hash каталога. Production
> не трогай.

## Где теперь старые обрезанные изображения?

В текущем `landing-granit-static/main` и на preview их быть не должно. Gate не
разрешит снова выложить старый commit вместо текущего `main`.

Старые байты могут оставаться в истории Git. Это нормально для отката и не
влияет на сайт. Полное вычищение Git history переписывает SHA всех веток и
ломает незавершённую работу, поэтому его нельзя смешивать с обычным deploy.

## Можно ли удалять старые releases, images и логи?

Да, но отдельной задачей. Во время обычного deploy ничего массово удалять не
надо.

Безопасное правило:

- сохранить текущую связку;
- сохранить одну предыдущую совместимую связку для отката;
- удалить временные файлы и незавершённые сборки;
- старые Docker images и release-каталоги удалять только после проверки, что на
  них не указывают staging и production;
- production releases не удалять без отдельного разрешения.

Пример запроса:

> Проведи read-only инвентаризацию старых staging releases, images и логов.
> Покажи, что можно удалить, сколько места это освободит и что останется для
> отката. Ничего не удаляй до моего подтверждения.

## Где лежит источник истины

- Код и файлы лендинга: `landing-granit-static/main`.
- Канонический индекс: `assets/catalog/catalog-index.v1.json` в лендинге.
- Копия для RAG: pinned snapshot в `granit-operations`.
- Фактически работающая связка: `/release.json` и backend `/health`.

Исторические отчёты и названия веток не доказывают, что версия сейчас работает.
Для staging смотрите runtime SHA и hash каталога.
