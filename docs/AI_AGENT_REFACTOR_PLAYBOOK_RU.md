# Рабочее руководство Codex по рефакторингу AI-слоя

Статус: действует для будущего рефакторинга AI-слоя

Владелец процесса: владелец проекта

Подробная исследовательская основа:
`docs/architecture/AI_REFACTOR_AGENT_GOVERNANCE_DESIGN_RU.md`

## 1. Зачем нужен этот документ

Этот документ превращает большую архитектурную схему в последовательность
маленьких проверяемых срезов.

Он отвечает на практические вопросы:

- какую модель открыть;
- что именно поручить ей в текущем запуске;
- что она имеет право менять;
- когда она обязана остановиться;
- кто независимо проверяет результат;
- как владелец подтверждает понимание выполненной работы.

Архитектурная записка хранит исследование и обоснование. Ежедневная работа
ведётся по этому руководству и по документу текущего среза.

## 2. Что делает владелец

Для одного среза владелец последовательно переключает модели:

1. GPT-5.6 Sol — Архитектор.
2. GPT-5.5 с `xhigh` — Исполнитель.
3. GPT-5.4 с `high` — Исследователь кода.
4. GPT-5.6 Sol — независимый Проверяющий.
5. При замечаниях GPT-5.5 с `xhigh` — Исправление.
6. После принятия GPT-5.6 Sol — Учитель.

Каждый пункт — отдельный запуск. Модели не запускаются параллельно.

В конце каждого запуска Codex обязан подготовить короткий блок
`Следующий запуск`, который владелец может вставить в новую задачу после выбора
указанной модели.

### 2.1 Что делать с будущей схемой AI-слоя

Не нужно вставлять всю исследовательскую спеку в каждый запрос.

Когда схема будет готова:

1. передать её Codex и написать: «Работай как Архитектор. Создай один первый
   срез по шаблону; рабочий код не меняй»;
2. дождаться заполненного контракта с вариантами, границами, лимитом и
   критериями успеха;
3. одобрить или исправить контракт;
4. открыть отдельный запуск на указанной в блоке `Следующий запуск` модели;
5. повторять последовательность ролей до `understanding_verified`;
6. только после остановки выбрать следующий срез.

Корневой `AGENTS.md` применяется автоматически. Руководство и текущий документ
среза агент обязан прочитать по его указанию.

## 3. Состояния одного среза

```text
baseline_checked
  -> slice_proposed
  -> scope_approved
  -> implementing
  -> technical_done
  -> code_scout_done
  -> independent_review
      -> needs_fix -> repairing -> technical_done
      -> needs_evidence
      -> needs_redesign -> slice_proposed
      -> needs_human_decision
      -> accept
  -> teaching
  -> understanding_verified
  -> stopped
```

Срез закрывается только после `understanding_verified`. Статусы
`technical_done` и `accept` не разрешают начинать следующий срез.

## 4. Первая будущая задача

До реализации новой схемы AI-слоя нужен отдельный срез сверки исходного
состояния.

Причина:

- в текущем коде одновременно присутствуют app-owned grounded runtime и части
  старого Mastra/live-v2;
- `ADR-010` и текущий код могут противоречить друг другу;
- в миграциях БД есть повторяющиеся номера;
- исторические документы и фактический `main` расходятся.

Первый срез должен только:

1. зафиксировать текущий SHA и состояние рабочей копии;
2. проверить код, ADR, задачи, миграции и архитектурные тесты;
3. составить карту действующего и устаревшего AI-кода;
4. предложить варианты получения единственного воспроизводимого исходного
   состояния;
5. не реализовывать новую архитектуру.

## 5. Контракт среза

Каждый срез создаётся по
`docs/tasks/AI_REFACTOR_SLICE_TEMPLATE_RU.md`.

До реализации владелец должен одобрить:

### 5.1 Один результат

Результат формулируется как наблюдаемое состояние, а не как процесс.

Хорошо:

> Единственный основной AI-runtime выбран, его граница закреплена тестом, а
> устаревшие пути перечислены без удаления.

Плохо:

> Разобраться с AI-кодом и по возможности улучшить архитектуру.

### 5.2 Критерии успеха

Критерии должны позволять однозначно ответить, закончена ли задача.

Каждый критерий содержит:

- проверяемое утверждение;
- команду, тест или другой способ доказательства;
- ожидаемый результат;
- поведение при невозможности проверки.

### 5.3 Область работы

Нужно перечислить:

- разрешённые файлы рабочего кода;
- разрешённые тесты;
- разрешённые документы и отчёты;
- затрагиваемые модули и контракты;
- явные исключения.

Каталог или общая формулировка вроде `apps/api/src/modules/ai/**` допускается
только для среза исследования без записи рабочего кода. Исполнитель получает
более узкий список.

### 5.4 Лимит изменений

До реализации задаются:

- максимальное число файлов рабочего кода;
- ориентир добавленных или изменённых строк рабочего кода;
- разрешённое число новых файлов;
- отдельный лимит для тестов и проверочного кода.

При превышении ориентира рабочего кода более чем на 50% Исполнитель
останавливается. Он не повышает лимит самостоятельно.

Большое удаление или механическое перемещение оценивается также по количеству
затронутых модулей и контрактов.

### 5.5 Условия остановки

Немедленно остановиться, если:

- нужен файл или модуль вне одобренного списка;
- требуется новая архитектурная развилка;
- затрагивается незаявленная миграция БД;
- меняется публичный контракт;
- меняются промпт, инструмент, модель или AI-policy;
- меняются приватность, send-time gate или manager takeover;
- возникает влияние на другой репозиторий;
- тест показывает необходимость соседнего рефакторинга;
- критерии успеха уже выполнены.

Соседняя работа записывается в раздел `Кандидат следующего среза`.

## 6. Роль Архитектора — GPT-5.6 Sol

### Разрешено

- читать код и документы;
- запускать безопасные проверки;
- обновлять только документ текущего среза;
- предлагать варианты и критерии.

### Запрещено

- писать рабочий код;
- исправлять найденные проблемы;
- расширять срез без владельца;
- начинать Исполнителя или другой срез.

### Обязательный результат

Архитектор:

1. проверяет исходный SHA и незавершённые изменения;
2. находит действующие источники истины;
3. фиксирует противоречия;
4. предлагает 2–3 варианта, если существует реальная развилка;
5. сравнивает риск, объём изменений, обратимость и доказательства;
6. рекомендует один вариант;
7. заполняет контракт среза;
8. просит владельца одобрить область и лимит;
9. останавливается.

Для механической задачи достаточно объяснить, почему реальной развилки нет.

### Начальный запрос

```text
Роль: Архитектор.
Модель: GPT-5.6 Sol.

Прочитай AGENTS.md, docs/AI_AGENT_REFACTOR_PLAYBOOK_RU.md и указанный документ
задачи. Работай только с одним срезом.

Проверь фактическое исходное состояние по текущему SHA. Найди противоречия между
кодом, ADR, задачами и тестами. Предложи реальные варианты решения с рисками,
объёмом изменений, обратимостью и доказательствами.

Не меняй рабочий код. Заполни только документ среза и остановись для одобрения
владельцем.
```

## 7. Роль Исполнителя — GPT-5.5 xhigh

### Разрешено

- менять только одобренные файлы;
- добавлять только одобренные тесты;
- запускать предусмотренные проверки;
- обновлять разделы выполнения и доказательств документа среза.

### Запрещено

- менять архитектурное решение;
- проводить широкую чистку;
- добавлять абстракции «на будущее»;
- переименовывать соседний код;
- повторять уже завершённую работу;
- принимать собственный результат.

### Порядок

1. Сверить модель, роль, SHA и статус `scope_approved`.
2. Проверить список разрешённых файлов и лимит.
3. Для исправления дефекта сначала добавить воспроизводящий тест.
4. Для рискованной гипотезы сначала использовать изолированный прототип или
   проверочный стенд.
5. Внести минимальное законченное изменение.
6. Запустить целевые тесты после изменения поведения.
7. Запустить остальные обязательные проверки.
8. Проверить полный набор изменений.
9. Записать непроверенные области.
10. Поставить `technical_done` и остановиться.

### Начальный запрос

```text
Роль: Исполнитель.
Модель: GPT-5.5, reasoning xhigh.

Реализуй только одобренный срез из указанного документа задачи. Не меняй
архитектурное решение и не выходи за разрешённые файлы или лимит изменений.

При новой развилке, незаявленной зависимости или превышении лимита остановись.
После критериев успеха не продолжай полировку.

Запусти обязательные проверки, запиши доказательства, выставь technical_done и
остановись. Не принимай собственную работу.
```

## 8. Роль Исследователя кода — GPT-5.4 high

Исследователь кода работает свежим запуском и не редактирует код.

Он ищет:

- все места вызова и использования изменённых интерфейсов;
- скрытые зависимости и область влияния;
- устаревшие и дублирующие пути выполнения;
- ошибки идемпотентности и повторов;
- гонки и проблемы конкурентного выполнения;
- необработанные сценарии отказа;
- слабые, отсутствующие или ложно-зелёные тесты;
- нарушения границ модулей и публичных контрактов;
- конфликты типов и миграций;
- утечки персональных данных, секретов и небезопасные логи.

Каждая находка обязана содержать:

- файл и точную строку;
- наблюдаемое доказательство;
- последствие;
- способ воспроизведения или проверки;
- уровень уверенности;
- неизвестные обстоятельства.

Гипотеза без доказательства отмечается как гипотеза.

### Начальный запрос

```text
Роль: Исследователь кода.
Модель: GPT-5.4, reasoning high.

Не меняй код. Изучи одобренный контракт, base/head SHA и полный diff. Ищи по
коду проблемы, которые могли пропустить Архитектор и Исполнитель: callers,
скрытые пути, ошибки отказа, идемпотентности, concurrency, границ, типов, тестов,
миграций, PII и логирования.

Каждую находку подкрепи точной локацией, доказательством, последствием и способом
проверки. Запиши отчёт только в разрешённое место и остановись.
```

## 9. Роль независимого Проверяющего — GPT-5.6 Sol

Проверяющий не редактирует код и сначала делает собственный проход. После этого
он проверяет находки Исследователя кода.

### Карта затронутых областей

Обязательно проверить:

- модули, интерфейсы и зависимости;
- БД, миграции и владение состоянием;
- обычное поведение и сценарии отказа;
- промпты, инструменты, настройки моделей и AI-policy;
- приватность, send-time gate и manager takeover;
- тесты, наборы оценки и наблюдаемость;
- развёртывание и откат;
- потребителей в других репозиториях.

### Допустимые вердикты

- `accept`;
- `needs_fix`;
- `needs_evidence`;
- `needs_redesign`;
- `needs_human_decision`.

Проверяющий предлагает более узкое или безопасное решение только при
существенной проблеме. Новизна сама по себе не является причиной переписывать
рабочий код.

### Начальный запрос

```text
Роль: независимый Проверяющий.
Модель: GPT-5.6 Sol.

Не меняй код. Проверь срез с нуля по контракту, base/head SHA, полному diff,
действующим ADR и доказательствам. Сначала сделай собственный проход, затем
проверь отчёт GPT-5.4.

Составь карту затронутых областей. Не доверяй отчётам предыдущих ролей без
проверки. Дай один из разрешённых вердиктов и запиши его в документ задачи.
Остановись, не исправляя код.
```

## 10. Роль Исправления — GPT-5.5 xhigh

Исправление остаётся внутри прежнего среза.

Разрешён один запуск Исправления. Он устраняет только подтверждённые замечания
внутри прежней области работы.

Если замечание требует нового файла, модуля, контракта или архитектурного
решения, запуск останавливается. Второй запуск Исправления требует нового
одобрения владельца и обновлённого лимита.

Повтор той же категории дефекта переводит срез в `needs_redesign` или
`needs_human_decision`.

## 11. Роль Учителя — GPT-5.6 Sol

Учитель запускается только после `accept`. Код больше не меняется.

### Цель

Владелец должен показать понимание:

1. причины проблемы и реальных развилок;
2. выбранного решения и главной альтернативы;
3. существенного краевого случая или сценария отказа;
4. доказательств и признака ошибочного результата;
5. влияния на систему и границы следующего среза.

### Порядок

1. Попросить владельца своими словами пересказать понимание.
2. Сверить ответ с живым контрольным списком в документе задачи.
3. Задавать ровно один вопрос за раз.
4. Не раскрывать правильный ответ до ответа владельца.
5. При необходимости показывать код, тесты, трассировки или отладчик.
6. Объяснять «почему», затем проверять «что» и «как».
7. Разрешать паузу, упрощение и короткий итог.

Пауза оставляет статус `teaching_paused`. Следующий срез остаётся
заблокированным.

### Начальный запрос

```text
Роль: Учитель.
Модель: GPT-5.6 Sol.

Прочитай принятый контракт, diff, независимый review и живой контрольный список
понимания. Не меняй код и не начинай следующий срез.

Сначала попроси меня своими словами пересказать, как я понял проблему, решение
и последствия. Затем закрывай пробелы по одному вопросу за раз. Не показывай
правильный ответ до моего ответа.

Срез можно закрыть только когда я объясню причину и развилки, обосную решение
против альтернативы, разберу существенный краевой случай, назову доказательства
и объясню влияние на систему.
```

## 12. Доказательства технического результата

До `technical_done` требуются:

- исходный и итоговый SHA;
- полный список затронутых файлов;
- `git diff --stat`;
- `git diff --check`;
- целевые тесты;
- проверка типов и линтер, если применимы;
- сборка затронутого пакета;
- тесты архитектурных границ;
- применимые локальные наборы оценки;
- минимальная сквозная проверка, если она безопасна и бесплатна;
- список непроверенных областей;
- способ отката или безопасного отказа от изменения.

Платная оценка на живой модели, миграции, изменения секретов, тестовая или
рабочая среда требуют отдельного разрешения владельца.

Если обязательную проверку нельзя выполнить, используется статус
`needs_evidence`.

## 13. Формат передачи следующему запуску

Каждая роль заканчивает работу следующим блоком:

```text
Следующий запуск

Роль: <роль>
Модель и reasoning: <точное значение>
Документ среза: <путь>
Исходный SHA: <sha>
Текущий SHA: <sha>
Текущий статус: <status>
Разрешённая запись: <точные файлы или "только чтение">
Обязательный вход: <контракт, diff, отчёты, доказательства>
Ожидаемый результат: <один результат>
Условия остановки: <условия>
```

Подготовка этого блока не запускает следующую роль автоматически.

## 14. Чего агент не делает

- Не запускает субагентов.
- Не использует Terra или Ultra.
- Не выполняет весь план рефакторинга за один запуск.
- Не продолжает после достижения критериев успеха.
- Не делает широкую чистку «раз уж мы здесь».
- Не принимает ответ другой модели без проверки по коду.
- Не считает отсутствие доказательств фактическим отсутствием проблемы.
- Не выдаёт исторический отчёт за доказательство текущего состояния.
- Не смешивает модель coding-agent с моделью клиентского AI-runtime.
