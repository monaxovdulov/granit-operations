Главная мысль

Мы не строим enterprise-архитектуру. Для Granit правильная цель другая: маленькая надежная система, которую понимает человек и которую AI-агент может безопасно менять через месяц.

Рабочая формула: Boring runtime, explicit boundaries, executable checks, short local docs, small agent tasks.

На практике это значит: один backend, один Postgres как source of truth, понятные модули внутри монолита, короткие task packs, ADR только для настоящих boundary decisions, проверки как evidence.

Карта backend flow

В нашем разговоре вся архитектура сводилась к простой цепочке. Это почти как FastAPI приложение с service layer и Protocol для базы.

Route / webhook

Принимает HTTP или provider update. Не держит бизнес-логику.

Service / use case

Решает сценарий: принять форму, сохранить сообщение, взять takeover.

Port / contract

Interface: какие возможности нужны service.

Repository

Реализация persistence. Сейчас это Postgres implementation.

Postgres

Source of truth: leads, conversations, messages, evidence.

HTTP route / webhook
  -> service / use case
  -> repository interface / port
  -> Postgres implementation
  -> database

Python → TypeScript перевод

Если ты Python-разработчик, самый близкий перевод такой:

В Python В нашем TypeScript коде Смысл
FastAPI endpoint Fastify route HTTP-адаптер: принимает request, вызывает use case, возвращает response.
application service PublicIntakeService, ManagerLeadUseCases Сценарий приложения без SQL и без raw HTTP деталей.
Protocol / ABC interface PublicIntakeRepository Контракт возможностей, от которого зависит service.

SQLAlchemy / asyncpg class PostgresIntakeRepository Реальная реализация сохранения в Postgres.

Словарь концептов

Intake прием обращения

В Granit это момент, когда внешний клиент впервые входит в систему: форма на сайте, site widget, Telegram inbound. 

client input enters the system
Persistence сохранение

Запись в постоянное хранилище, у нас в Postgres. Не просто держать в памяти, а надежно сохранить lead, conversation, message, evidence. 

intake persistence =
прием обращения + запись в Postgres
DTO Data Transfer Object

Простой объект передачи данных. Не “умная” бизнес-сущность, а явная форма: какие поля нужно передать между слоями. 

type SaveAcceptedSiteFormSubmissionInput = {
  publicSubmissionId: string;
  request: SiteFormIntakeRequest;
  requestFingerprint: string;
};
Repository обертка над persistence

Объект, который прячет SQL/Drizzle/Postgres details. Service вызывает понятный метод, repository знает, какие таблицы трогать. 

repository.saveAcceptedSiteWidgetMessage(...)
Contract типовое обещание

Описание, какие методы и данные доступны. В TypeScript это обычно interface или type. 

contract говорит ЧТО доступно,
но не говорит КАК это реализовано
Port interface между слоями

Не TCP-порт. Это архитектурный “разъем”: service зависит от interface, а не от Postgres-класса. 

PublicIntakeRepository = port
PostgresIntakeRepository = implementation
Aggregate repository contract собранный контракт

Большой интерфейс, который объединяет несколько маленьких repository contracts. Он нужен для compatibility, но новому коду лучше брать narrow port. 

interface IntakeRepository
  extends PublicIntakeRepository,
    ConversationMessageRepository,
    ManagerLeadRepository,
    ManagerTelegramRepository {}
Public intake scenarios клиентские входные сценарии

Тесты, которые проверяют внешний вход: сайт-форма и site widget. Например: валидная форма, validation error, idempotency, AI fallback. 

valid form -> lead saved
invalid form -> typed validation error
same request -> no duplicate lead

Что поменяли в P1-1

Был один большой file-level import target: intake-repository.ts. Он уже содержал логически хорошие интерфейсы, но они были физически спрятаны в одном broad file.

Было
intake-repository.ts экспортировал shared types, public intake DTO, conversation message DTO, manager lead port, manager Telegram port и aggregate IntakeRepository.
Стало
Контракты разнесены по файлам: lead-conversation-types.ts, public-intake-repository.ts, conversation-message-repository.ts, manager-lead-repository.ts, manager-telegram-repository.ts.
Compatibility
Старый IntakeRepository сохранен как aggregate compatibility interface. Legacy exports under apps/api/src/repositories/* тоже сохранены.

Это не перенос behavior. Это contract/type split. Postgres queries, DB schema, migrations, env names, npm scripts and runtime topology не менялись.

Почему это не enterprise

Важно: слова repository, DTO, port, contract могут звучать enterprise-но. Но в Granit они используются в маленькой практичной версии.

Enterprise-вариант, который нам не нужен

  • generic Repository<T>;
  • Unit of Work ради паттерна;
  • DI container;
  • CQRS/event bus без реальной боли;
  • микросервисы на ранней стадии;
  • DTO на каждый слой без пользы.

Наш вариант

  • один ops-api service;
  • один Postgres source of truth;
  • маленькие explicit interfaces по ответственности;
  • repository methods под реальные business actions;
  • DTO только на важных границах;
  • проверки там, где есть риск потерять lead/message/evidence.
Если тип защищает важную границу - оставляем.
Если тип просто переименовывает тот же объект без пользы - не добавляем.

Best practices: кто пишет про простые решения

37signals / Basecamp

Jason Fried, DHH, Ryan Singer: маленькие команды, меньше процесса, меньше unnecessary software, реальные shipped features. Полезные источники: Getting Real и Shape Up. 

Не строить систему “на вырост”.
Строить маленький надежный продукт,
который решает реальную боль.

DHH / Rails monolith culture

Идея: монолит не проблема, проблема - неструктурированный монолит. Полезно смотреть Rails Doctrine и материалы DHH про monoliths. 

Один deployable app,
понятные внутренние модули,
простая эксплуатация.

Dan McKinley: Choose Boring Technology

Choose Boring Technology хорошо объясняет, почему новый tech stack тратит innovation budget. 

Postgres, Fastify, TypeScript, Vitest.
Без Kafka/Redis/Kubernetes,
пока боль не доказана.

Martin Fowler: Monolith First

Monolith First: начинать с монолита, а сервисы выделять только когда границы и боль стали ясны. 

Сначала modular monolith.
Потом, если реально нужно,
выделение частей.

John Ousterhout

A Philosophy of Software Design полезна идеей deep modules: простой interface, который скрывает реальную сложность. 

PublicIntakeRepository снаружи простой.
Postgres внутри может быть сложным.

Matt Pocock / Dan Vanderkam

Matt Pocock помогает писать понятный TypeScript, Dan Vanderkam в Effective TypeScript помогает думать о типах как о способе представлять valid states. 

DTO / union / literal types -> type
capability contracts -> interface

Frozen validation: как лучше формулировать

В repo docs не было закрепленного термина frozen validation. Поэтому лучше не использовать его как магическое слово. Нужна точная формулировка: что именно заморожено и что можно менять.

Рекомендуемая формулировка: Public validation contract is compatibility-frozen for v1. Internal validation implementation may be refactored only when evidence shows public behavior is unchanged. 

Public validation contract is compatibility-frozen for v1.
Internal validation implementation may be refactored only when evidence shows:
1. typed validation errors still return the same public shape;
2. unsupported-version behavior is unchanged;
3. retry/fallback behavior is unchanged;
4. accepted requests are persisted before success is reported;
5. no false public success is introduced.

По-русски: мы замораживаем внешний контракт ошибок для сайта/клиента, но не запрещаем улучшать внутреннюю реализацию, если тесты и evidence доказывают то же поведение.

Практические правила для Granit

Делать

  • Оставлять ops-api одним service, пока нет доказанной причины.
  • Держать Postgres source of truth для leads, messages, delivery evidence.
  • Делать small refactor slices с explicit out of scope.
  • Писать repository methods как business actions.
  • Использовать DTO на boundary, где они реально защищают контракт.
  • Добавлять checks as evidence, а не просто “я думаю работает”.
  • Оставлять compatibility exports, если release phase этого требует.

Не делать без явной причины

  • microservices;
  • event bus;
  • DI container;
  • generic repository layer;
  • CQRS;
  • широкий rewrite;
  • omnichannel CRM / WhatsApp / MAX / call tracking вне scope;
  • изменение public API, DB schema, env names, npm scripts без acceptance criteria.
Новая абстракция допустима только если она:
1. уменьшает реальную сложность;
2. защищает важную границу;
3. убирает значимое дублирование;
4. делает тестирование надежнее;
5. соответствует уже существующему стилю проекта.

Самопроверка понимания

Если ты понял, ты можешь объяснить так

Intake persistence - это прием клиентского обращения и надежная запись фактов в Postgres.

Port - это interface, от которого зависит use case, чтобы не знать про SQL/Drizzle/Postgres details.

DTO - это явная форма данных на границе, похожая на dataclass, TypedDict или Pydantic model.
