# Минимальный Goal-контур AI-рефакторинга

Статус: принят владельцем 2026-08-03

Актуализация 2026-08-24: правила одной Goal, одного среза и независимой приёмки
остаются действующими. Первоначальный roadmap PR0a—PR9 ниже и завершённая Goal
`AI-RUNTIME-CONVERGENCE` являются историческим baseline. Текущий порядок задаёт
`docs/tasks/AI_LAYER_SIMPLIFICATION_GOAL_RU.md` и её единственная active card.

Репозиторий: `granit-operations`

Заменяет ежедневный шестиролевой governance-v1. Старый design удалён из
active tree в CONV-4; его исследовательский provenance остаётся в Git history
и `docs/tasks/ARCHIVE_RU.md`.

## 1. Решение владельца

Владелец решил упростить процесс и вести весь актуальный AI-roadmap внутри
одной долгоживущей Goal вместо ручного запуска каждой роли и каждого среза.

Активная Goal:

- thread ID: `019fc912-6005-73f2-ba46-ccb40eb26334`;
- первоначальный порядок: `PR0a -> PR0b -> PR0c -> PR1 -> ... -> PR9`;
- один технически активный срез;
- автоматический переход к следующему после независимого `accept`;
- общий teach-back после завершения roadmap.

Goal сохраняет цель и прогресс. Она не даёт разрешения на commit, push, merge,
deploy, секреты, платные вызовы или другой репозиторий вне явно заданного scope.

## 2. Почему старый процесс упрощён

Governance v1 обеспечил полезные свойства:

- не дал начать новую архитектуру до baseline reconciliation;
- обнаружил конфликт migrations и false-green PostgreSQL evidence;
- разделил автора и принимающего;
- сохранил dirty worktree и решения владельца.

Но после этого его стоимость стала непропорциональной:

- шесть ролей на каждый малый diff;
- повторные ручные одобрения файлов и строк;
- отдельный Code Scout, повторяющий значительную часть Reviewer;
- обязательная точная модель как процессный blocker;
- task docs длиннее реализации;
- Teach-back между связанными техническими шагами;
- невозможность Goal автоматически продолжать заранее утверждённый roadmap.

Это увеличивает переключение контекста и создаёт новый риск: процесс начинает
оптимизироваться под документы вместо результата системы.

## 3. Рассмотренные варианты

### Вариант A — оставить governance v1

Плюс: максимальная формальная изоляция ролей.

Минус: слишком высокая стоимость для roadmap PR0a–PR9; каждое исправление
проходит полный архитектурный и учебный цикл независимо от риска.

### Вариант B — одна Goal без промежуточных границ

Плюс: минимальное трение.

Минус: один большой diff, дрейф scope, смешивание migrations, behavior и
cleanup, принятие собственной работы и сложный rollback.

### Вариант C — одна Goal, последовательные срезы и независимый accept

Плюсы:

- цель и контекст сохраняются;
- roadmap продолжается автоматически;
- каждый diff остаётся проверяемым и откатываемым;
- Reviewer объединяет Code Scout и техническую приёмку;
- владелец подключается только к решениям с реальным риском.

Минус: требуется дисциплина обновлять компактную карточку и не смешивать
соседние PR.

Выбран вариант C.

## 4. Минимальные инварианты

Не упрощаются:

1. Одновременно изменяется один срез.
2. Автор рабочего diff не выдаёт себе независимый `accept`.
3. Каждый срез имеет воспроизводимые проверки и rollback.
4. Высокорисковая новая развилка возвращается владельцу.
5. Субагенты, Multi-agent, Terra и Ultra не используются.
6. Сохраняются чужие незавершённые изменения.

Всё остальное является маршрутом по умолчанию, а не неподвижным ритуалом.

## 5. Две обязательные роли

### Исполнитель

Владеет реализацией и repair внутри одного среза. Может выбирать обычные
детали реализации в пределах утверждённой архитектуры и модульной области.

### Независимый Проверяющий

Свежим проходом проверяет контракт и код. Включает функции прежнего Code Scout:
callers, скрытые paths, concurrency, migrations, false-green tests, privacy,
observability и rollback.

Автор не является независимым Reviewer собственного diff.

## 6. Необязательные роли

Архитектор нужен только при реальной развилке, меняющей архитектуру, ownership,
migration strategy или roadmap.

Учитель нужен один раз в конце Goal или крупной вехи. Отдельные срезы сохраняют
три коротких учебных факта: причина, доказательство, оставшийся риск.

Исправление не является отдельной ролью: Исполнитель обрабатывает подтверждённый
`needs_fix`. Повтор одной категории дефекта дважды вызывает `needs_redesign`.

## 7. Четыре стоп-гейта

Новое разрешение владельца требуется только для ещё не одобренного действия:

1. архитектурная развилка, roadmap или ownership;
2. migration/schema БД или публичный контракт;
3. prompt/tool/model-policy/privacy/send gate/takeover;
4. deploy/secrets/runtime config/платный вызов/другой repo.

Если точное действие уже одобрено в Goal или карточке, разрешение не
запрашивается повторно.

## 8. Бюджет изменений

Для обычного внутреннего среза число файлов и строк — ориентир. Reviewer
оценивает изменение по результату и blast radius.

Точный allowlist и hard limit обязательны только когда риск связан с:

- migration/schema;
- публичным контрактом;
- policy/privacy/send gate/takeover;
- deploy или другим repo;
- массовым механическим изменением.

Новый test/helper файл внутри прежнего модуля сам по себе не требует владельца.

## 9. Evidence и автоматический переход

Минимальная evidence:

- base/head SHA;
- затронутые файлы и `git diff --stat`;
- целевые тесты;
- применимые typecheck/build/boundary/integration checks;
- `git diff --check`;
- непроверенные области;
- rollback.

После `accept` Goal обновляет реестр и начинает baseline следующего заранее
указанного среза. Красная обязательная проверка, `needs_redesign` или один из
стоп-гейтов блокируют переход.

## 10. Исторический roadmap исходной Goal

```text
PR 0a  real PostgreSQL baseline
PR 0b  canonical AI schema/migration reconciliation
PR 0c  bounded hotfixes
PR 1   turn identity and commit fence
PR 2   latest-wins and fresh context
PR 3   ModelTurnOutput -> ValidatedTurnPlan -> CommittedTurn
PR 4   state patches and corrections
PR 5   bounded tools and retrieval v2
PR 6   risk-only verifier
PR 7   sticky runtime and read-only shadow
PR 8   observability and handoff UX
PR 9   structural cleanup
```

PR0b добавлен после evidence PR0a: текущий Drizzle `ai_runs` contract и
test-only active migration manifest не дают production-shaped grounded commit.
PR0c не начинается поверх этого недоказанного состояния.

## 11. Безопасная отмена

Владелец может остановить Goal или вернуть более строгий процесс. Тогда:

- текущий срез доводится до безопасной остановки;
- следующий автоматически не начинается;
- принятые diff/evidence сохраняются;
- новая governance не меняет production rollback уже выполненных срезов.
