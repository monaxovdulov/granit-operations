Repository contracts split: что поменялось и зачем

Этот документ объясняет slice P1-1 человеческим языком: где была проблема, что теперь стало правдой в системе, какие проверки это подтверждают, чему пока нельзя доверять и как лучше формулировать validation-границы дальше.

public API не менялся Postgres behavior не переносился IntakeRepository сохранен legacy exports сохранены production deploy не выполнялся

Короткая ориентация

Что теперь правда

Контракты conversation/intake persistence больше не живут одним большим списком в intake-repository.ts. Они разнесены по узким файлам под уже существующие ответственности.

Зачем проекту

Будущие работы вокруг Telegram, manager workflow и widget AI смогут зависеть от нужного порта, не подтягивая весь aggregate repository contract.

Можно ли доверять

Typecheck и два targeted Vitest проходят. Это доказывает, что TypeScript-контракты и public intake сценарии не сломались, но не является production smoke.

Было → стало

Было

Один файл apps/api/src/modules/conversations/repositories/intake-repository.ts одновременно экспортировал:

  • shared lead/conversation enums and errors;
  • public site form and widget persistence DTO;
  • conversation message persistence DTO;
  • manager lead read/mutation port;
  • manager Telegram binding/reply port;
  • aggregate IntakeRepository.
→

Стало

Тот же контрактный смысл разложен по файлам:

  • lead-conversation-types.ts — общие enums/errors;
  • public-intake-repository.ts — public intake port;
  • conversation-message-repository.ts — inbound/outbound message persistence port;
  • manager-lead-repository.ts — manager lead read/mutation port;
  • manager-telegram-repository.ts — manager Telegram binding/reply port;
  • intake-repository.ts — aggregate compatibility interface and re-export.

Почему это важно

Это не “архитектура ради архитектуры”. Разделение делает import graph честнее: public intake use case видит public intake port, manager use case видит manager port, timeline builders видят только shared types. Так будущий refactor меньше рискует случайно зацепить lead truth, takeover, delivery evidence или Telegram outbound policy.

Как это теперь работает

Public site form PublicIntakeService зависит от PublicIntakeRepository. Он валидирует contract input, считает fingerprint и сохраняет accepted submission через narrow persistence port.
Site widget PublicWidgetIntakeService тоже зависит от PublicIntakeRepository. AI reply generation и persistence sequencing не менялись.
Telegram inbound RepositoryTelegramInboundUseCases теперь описывает нужную комбинацию ports: conversation messages, manager Telegram binding/reply и takeover by public conversation id.
Manager panel Manager lead use cases зависят от ManagerLeadRepository, а Telegram binding use cases — от ManagerTelegramRepository.
Runtime assembly PostgresIntakeRepository все еще implements IntakeRepository. Это compatibility aggregate для текущего app context и tests, не новый runtime слой.

Что не менялось

Сохранено намеренно

  • public API request/response contracts;
  • DB schema and migrations;
  • env variable names;
  • npm scripts;
  • runtime topology;
  • Postgres as source of truth;
  • Telegram AI outbound block;
  • compatibility exports under apps/api/src/repositories/*.

Не является результатом slice

  • не выделялся новый service;
  • не добавлялся event bus;
  • не добавлялся DI container;
  • не переносилось поведение из PostgresIntakeRepository;
  • не делался production или staging deploy;
  • не проектировался omnichannel CRM, WhatsApp/MAX/call tracking.

Самое неожиданное

1. Порты уже были логически разделены, но физически спрятаны

В старом файле уже существовали PublicIntakeRepository, ConversationMessageRepository, ManagerLeadRepository и ManagerTelegramRepository. Неожиданность была в том, что boundary problem почти полностью был file-level: хорошие responsibility names жили внутри одного широкого import target.

2. Timeline зависел от aggregate ради нескольких shared types

timeline-events.ts не нужен весь repository contract. Ему нужны только enums вроде channel/status/content type. Это был простой, но показательный случай “случайной широкой зависимости”.

3. Tests intentionally keep legacy compatibility pressure

Public intake tests импортируют через ../src/repositories/intake-repository.js. Это не баг: так проверяется, что legacy compatibility export still works during this phase.

4. Task pack был untracked, а рядом были unrelated dirty docs

Это важно operationally: slice делался поверх уже dirty worktree. Я не трогал unrelated docs и не включал их в смысл P1-1, чтобы не смешивать чужие изменения с refactor evidence.

5. Термин “frozen validation” в repo docs не найден

В проекте есть validation/failure terminology для public intake, но нет закрепленного термина frozen validation. Значит, его лучше не использовать как будто он уже принят; ниже есть варианты reformulation.

Границы доверия

Этот slice повышает clarity of module boundaries, но не доказывает production readiness. Не было deploy, staging smoke, migration run или live traffic validation.

  • PostgresIntakeRepository все еще толстый implementation. Это осознанно: P1-1 split contracts before behavior movement.
  • Compatibility aggregate still exists. Новому коду лучше импортировать narrow ports, но старые callers не ломаются.
  • Contract split не меняет бизнес-истину: реальные lead/conversation/delivery facts остаются в Postgres, а не в UI state, traces или prompt text.

Proposals: “frozen validation” reformulation

В текущих docs нет принятого термина frozen validation. Ниже варианты, которые лучше объясняют, что именно нельзя менять без отдельного решения.

Option A: “Compatibility-frozen public validation”

Смысл: public validation response shape is frozen for current contract version. Можно рефакторить internals, но нельзя менять внешний формат ошибок без versioned contract change. 

Public validation response shape is compatibility-frozen for v1.

Лучше всего для docs/contracts and public intake tasks.

Option B: “Evidence-gated validation changes”

Смысл: validation logic можно менять, но только с тестами/evidence, которые показывают typed validation, retry/fallback и no false success behavior. 

Validation changes are evidence-gated, not casually editable.

Лучше всего для AGENTS-style guardrails and future task packs.

Option C: “Public contract validation is frozen; internal mapping is not”

Смысл: внешний contract остается стабильным, а внутренние файлы, ports и adapters можно переставлять, если compiled contracts and scenario tests pass. 

Freeze the public validation contract, not the internal implementation.

Лучше всего для refactor slices like P1-1/P2-3.

Recommended wording

Рекомендую использовать комбинированную формулировку: 

Public validation contract is compatibility-frozen for v1.
Internal validation implementation may be refactored only when evidence shows:
1. typed validation errors still return the same public shape;
2. unsupported-version behavior is unchanged;
3. retry/fallback behavior is unchanged;
4. accepted requests are persisted before success is reported;
5. no false public success is introduced.

Почему так лучше: она разделяет contract freeze и implementation freedom. Это защищает сайт и пользователей от breaking changes, но не блокирует безопасный backend refactor.

План дальше

  1. P1-2: вынести manager Telegram persistence behavior из PostgresIntakeRepository в отдельный implementation module, сохранив facade/aggregate там, где он нужен app context.
  2. После P1-2: проверить, что Telegram inbound still has no provider send path, delivery still does not depend on webhook/inbound, and Postgres remains source of truth.
  3. Для validation wording: добавить выбранную формулировку в ближайший relevant task pack или contracts doc, но не смешивать это с behavior refactor без отдельной acceptance criteria.
