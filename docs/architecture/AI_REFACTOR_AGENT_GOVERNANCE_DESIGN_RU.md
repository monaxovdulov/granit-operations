# Проект правил управления Codex при рефакторинге AI-слоя

Статус: реализовано в правилах работы Codex

Дата: 2026-07-30

Репозиторий: `granit-operations`

Область документа: порядок работы агента-разработчика при будущем рефакторинге
AI-слоя

Рабочие файлы:

- `AGENTS.md`;
- `docs/AI_AGENT_REFACTOR_PLAYBOOK_RU.md`;
- `docs/tasks/AI_REFACTOR_SLICE_TEMPLATE_RU.md`.

Этот документ хранит исследование и обоснование решений. Для ежедневной работы
используются три рабочих файла выше.

Не относится к рабочему AI-контуру: клиентские промпты, правила выбора моделей,
инструменты AI-консультанта и включение AI в рабочей среде

## 1. Цель

Создать компактный и автоматически применяемый контракт, который управляет Codex
при будущем рефакторинге AI-слоя.

Контракт должен:

- удерживать одну проверяемую область работы за запуск;
- не позволять агенту самовольно расширять задачу;
- разделять архитектуру, реализацию, поиск пропущенных проблем в коде и итоговую
  независимую проверку;
- ограничивать объём изменений рабочего кода;
- требовать воспроизводимые доказательства результата;
- не разрешать автору самостоятельно принять собственную работу;
- после технического результата проверять понимание владельца;
- блокировать следующий срез до закрытия технической проверки и проверки
  понимания.

Будущая схема AI-слоя, которую предоставит владелец, будет отдельным входным
архитектурным контрактом. Этот документ не пытается заранее придумать или
реализовать её.

### 1.1 Термины документа

- **Срез (`slice`)** — одна небольшая законченная техническая задача с одним
  результатом.
- **Исходное состояние (`baseline`)** — проверенное состояние кода, документов и
  тестов до начала изменений.
- **Набор изменений (`diff`)** — разница между состоянием до и после работы.
- **Рабочий код (`production code`)** — код приложения, который может попасть в
  рабочую среду; тесты и одноразовые проверочные программы учитываются отдельно.
- **Область влияния (`blast radius`)** — все прямые и косвенные части системы,
  которые может затронуть изменение.
- **Независимая проверка (`review`)** — проверка результата свежим запуском
  модели, которая не писала этот код.
- **Обратное объяснение (`teach-back`)** — владелец своими словами объясняет
  проблему, решение и последствия, чтобы показать реальное понимание.
- **Доказательства (`evidence`)** — тесты, проверки, логи, снимки состояния и
  другие воспроизводимые подтверждения результата.

## 2. Почему нужен отдельный контракт

GPT-5.6 Sol способен уверенно вести длинные задачи, но его полезная инициативность
может перейти в лишние действия, повторные вызовы инструментов, слишком широкий
набор изменений и продолжение работы после достижения основного результата.

Обычного пожелания «не делай лишнего» недостаточно. Нужны наблюдаемые границы:

- один ожидаемый результат;
- утверждённый список разрешённых файлов и областей;
- измеримые критерии завершения;
- лимит изменений рабочего кода;
- явные условия остановки;
- независимая проверка;
- запрет перехода к следующему срезу.

При этом нельзя превращать системный промпт в длинный список повторяющихся
запретов. Постоянный контекст должен содержать только инварианты и маршруты к
детальным инструкциям.

## 3. Проверенные источники и границы применимости

### 3.1 Официальная документация OpenAI

Нормативные рекомендации для GPT-5.6 берутся из:

- [Руководство по промптам для GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6);
- [Руководство по моделям GPT-5.6](https://developers.openai.com/api/docs/guides/latest-model);
- [Руководство по работе нескольких агентов](https://developers.openai.com/api/docs/guides/responses-multi-agent);
- [Руководство по глубине рассуждений](https://developers.openai.com/api/docs/guides/reasoning);
- [Постановка задач Codex и ChatGPT](https://learn.chatgpt.com/docs/prompting);
- [Постоянные инструкции в AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md);
- [Системная карта GPT-5.6](https://deploymentsafety.openai.com/gpt-5-6).

Подтверждённые выводы:

- промпт должен прежде всего задавать результат, необходимые доказательства,
  ограничения, критерии успеха и условия остановки;
- каждое постоянное правило следует формулировать один раз;
- `ALWAYS`, `NEVER`, `must` и `only` нужны только для настоящих инвариантов;
- повторяющиеся инструкции о процессе и стиле, а также нерелевантные инструменты
  стоит удалять;
- упрощение промпта надо проверять на собственных наборах оценки (`evals`), а не
  считать универсальным улучшением;
- `text.verbosity` управляет формой текстового ответа, но не ограничивает объём
  кода или внутреннюю инициативность агента;
- глубину рассуждений (`reasoning effort`) повышают только после проверки на
  репрезентативных задачах;
- сохранение рассуждений между ходами полезно при стабильной цели, но устаревшие
  рассуждения могут привязать модель к старому подходу;
- несколько агентов полезны для независимых ограниченных направлений работы, но
  увеличивают расход токенов и затраты на координацию.

OpenAI приводит внутреннюю оценку агента-разработчика, где более короткие
системные промпты дали примерно `+10–15%` к результату оценки, `−41–66%` токенов
и `−33–67%` стоимости. Эти диапазоны являются направляющими результатами
внутренней оценки, а не гарантией для этого проекта.

### 3.2 Исследование Toloka

[Исследование Toloka о настойчивости GPT-5.6](https://toloka.ai/blog/gpt-5.6-got-smarter-then-it-kept-acting/)
сообщает результаты на наборе из 711 закрытых корпоративных сценариев с
проверкой итогового состояния БД.

Корректное прочтение чисел:

- Sol при среднем уровне рассуждений (`medium`) был примерно на `3.7`
  процентного пункта ниже GPT-5.5 при том же уровне;
- Terra при среднем уровне рассуждений был примерно на `8.7` процентного пункта
  ниже GPT-5.5 при том же уровне;
- рост точных повторов вызова одного инструмента был диапазоном, а `+8.5` п.п. —
  максимум для одного из сравнений, не универсальное значение Sol;
- метрика попытки возврата значения измеряла последовательность `A -> B -> A`,
  но не доказывала, что `A` было правильным, а `B` промежуточным;
- рост лишних записей также был диапазоном, а не единым значением для всех
  конфигураций.

Это самостоятельная публикация компании, а не рецензируемая научная работа.
Пакет материалов содержит данные и скрипты, но полные закрытые задачи и исходные
траектории работы модели не опубликованы, поэтому независимая полная репликация
невозможна.

Системная карта OpenAI отдельно показывает снижение метрики `Avoidance only` с
`0.88` для GPT-5.5 до `0.83` для Sol. Эта оценка проверяет сохранение
пользовательских изменений и данных при потенциально разрушительных действиях,
а не является общим «индексом предотвращения опасных команд».

Практический вывод для этого проекта: исследование поддерживает необходимость
явных условий остановки и проверки конечного состояния, но не доказывает, что
GPT-5.6 всегда хуже GPT-5.5.

### 3.3 Материалы Anthropic

Материалы Anthropic полезны как независимый источник принципов проектирования
контекста:

- [Новые правила проектирования контекста](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models);
- [Эффективное проектирование контекста для AI-агентов](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents);
- [Построение циклов проверки](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills);
- [Проверочная среда для каждой задачи](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code).

Полезные общие идеи:

- корневой файл инструкций должен быть коротким маршрутизатором;
- подробности загружаются по мере необходимости (`just in time`);
- тесты, типы, ошибки выполнения и проектные проверки образуют цикл проверки;
- большой одноразовый проверочный стенд допустим, если изменения рабочего кода
  остаются узкими;
- параллельная работа имеет смысл только при изолированных целях и состоянии.

Это рекомендации для Claude. Их нельзя автоматически переносить на GPT-5.6 без
проектных оценок.

### 3.4 Предоставленное видео

[Видео «Вы читаете слишком много кода»](https://www.youtube.com/watch?v=434cG4g5KLE)
является авторским опытом, а не исследованием.

Используемый инженерный вывод:

- можно дёшево создавать одноразовые отладчики, линтеры, проверочные стенды и
  конкурирующие прототипы;
- такие эксперименты должны быть изолированы от рабочего кода;
- большой объём вспомогательного проверочного кода не разрешает раздувать
  изменения рабочего кода;
- рабочий код всё равно требует чтения, тестов и независимой проверки.

История про 10 000 строк JavaScript не используется как количественный норматив.

## 4. Текущее исходное состояние репозитория

На момент исследования:

- `main == origin/main == ee77a35`;
- пользовательский каталог `output/` не отслеживается Git и не входит в область
  работы;
- последнее слияние вернуло значительную часть старого слоя Mastra/live-v2;
- `docs/tasks/RECONCILE_REMAINING_BRANCHES_RU.md` ранее пометил этот рабочий
  контур как `superseded` (заменённый более новой реализацией) и запретил
  переносить его как основную оркестрацию;
- принятый `ADR-010` оставляет основной AI-контур под управлением приложения;
- среди миграций БД одновременно присутствуют дубли номеров `0010`, `0011` и
  `0012`;
- существует `0016_widget_ai_jobs.sql`, хотя часть документации всё ещё говорит,
  что следующая миграция должна начинаться с `0016`;
- тест архитектурных границ запрещает ссылки на Mastra/live-v2 вне узких
  разрешённых точек интеграции.

Это означает, что первая техническая задача будущего рефакторинга должна быть
сверкой и приведением исходного состояния в порядок (`reconciliation`), а не
реализацией новой архитектуры.

Такая сверка обязана:

1. проверить код, документы, ADR, миграции и тесты на одном SHA;
2. определить единственный основной рабочий AI-контур;
3. отделить актуальную реализацию от устаревших и заменённых путей;
4. получить зелёное и воспроизводимое исходное состояние;
5. только после этого разрешить следующий архитектурный срез.

Эта спецификация не выполняет сверку и не утверждает заранее способ исправления.

## 5. Структура комплекта правил

### 5.1 Корневой `AGENTS.md`

Короткий автоматически загружаемый файл-маршрутизатор.

Он содержит только:

- порядок приоритета источников;
- обязательный порядок чтения;
- правило одного среза;
- запрет субагентов, Terra и Ultra;
- запрет самовольного расширения задачи;
- обязательные независимую проверку и проверку понимания;
- ссылки на рабочее руководство и шаблон среза.

Он не копирует подробные архитектурные, модельные или обучающие инструкции.

### 5.2 `docs/AI_AGENT_REFACTOR_PLAYBOOK_RU.md`

Подробное рабочее руководство:

- проверка источников и рекомендации по моделям;
- жизненный цикл среза;
- распределение моделей по ролям;
- контракт самостоятельной постановки задачи;
- границы и лимиты изменений;
- проверки и доказательства;
- исследование кода и независимая проверка;
- порядок исправлений;
- протокол обратного объяснения;
- правила остановки и передачи решения владельцу.

### 5.3 `docs/tasks/AI_REFACTOR_SLICE_TEMPLATE_RU.md`

Шаблон конкретной задачи:

- статус;
- исходный и итоговый SHA;
- источники истины;
- ожидаемый результат;
- альтернативы и принятое решение;
- критерии успеха;
- область работы и явные исключения;
- ожидаемый список файлов и модулей;
- лимит изменений;
- роли и модели;
- проверки и доказательства;
- находки и циклы исправления;
- контрольный список понимания;
- кандидат на следующий срез.

Будущая архитектурная схема владельца хранится отдельной спецификацией, ADR или
задачей и указывается в конкретном срезе. Она не встраивается целиком в
`AGENTS.md`.

## 6. Порядок приоритета источников

Внутри проектных инструкций более новый и конкретный принятый контракт имеет
приоритет над историческим документом:

1. текущая явная задача владельца;
2. отдельно одобренная архитектурная спецификация владельца;
3. принятые ADR и действующие источники истины;
4. одобренный контракт текущего среза;
5. руководство по рефакторингу AI-слоя;
6. исторические задачи, планы и отчёты прошлых проверок.

Исторический документ не становится действующим только из-за слов `active`,
`implemented` или `passed`. Агент сверяет дату, SHA, код и принятые ADR.

Если код, задача, ADR и документы противоречат друг другу, агент не выбирает
удобную версию молча. Он фиксирует конфликт и останавливается для сверки или
решения владельца.

## 7. Жизненный цикл одного среза

```text
baseline_checked
  -> slice_proposed
  -> scope_approved
  -> implementing
  -> technical_done
  -> code_scout_done
  -> independent_review
      -> needs_fix -> repairing -> technical_done
      -> needs_redesign -> slice_proposed
      -> accept
  -> teaching
  -> understanding_verified
  -> stopped
```

Значение состояний:

- `baseline_checked` — исходное состояние проверено;
- `slice_proposed` — срез предложен;
- `scope_approved` — область работы одобрена;
- `implementing` — идёт реализация;
- `technical_done` — реализация закончена и первичные проверки пройдены;
- `code_scout_done` — исследователь кода закончил отдельную проверку;
- `independent_review` — идёт независимая итоговая проверка;
- `needs_fix` — нужны исправления в прежней области работы;
- `needs_redesign` — требуется вернуться к выбору решения;
- `accept` — технический результат принят проверяющим;
- `teaching` — идёт проверка понимания владельца;
- `understanding_verified` — понимание подтверждено;
- `stopped` — запуск остановлен, следующий срез не начат.

Правила:

- одновременно активен только один срез;
- один запуск выполняет только одну роль;
- следующий срез не начинается автоматически;
- обнаруженная соседняя работа записывается как кандидат на следующий срез;
- `technical_done` не означает `accept`;
- вердикт `accept` не означает `understanding_verified`;
- только `understanding_verified` закрывает срез;
- после закрытия агент останавливается.

Пауза разрешена на любом этапе. Пауза не переводит задачу в принятый статус и не
разблокирует следующий срез.

## 8. Последовательные роли и модели

Субагенты, Terra и Ultra запрещены.

Для Архитектора, Исследователя кода, Проверяющего и Учителя режим «только чтение»
означает запрет на изменение рабочего кода, настроек выполнения, миграций,
тестов и продуктовых документов. Им разрешено обновлять только заранее
назначенный документ задачи, отчёт проверки или контрольный список понимания
текущего среза. Точные пути этих документов входят в одобренный список файлов.

### 8.1 Архитектор: GPT-5.6 Sol

Режим: отдельный запуск без изменения кода, исходное значение
`reasoning=medium`.

Обязан:

- проверить текущее исходное состояние;
- найти противоречия между источниками истины;
- сформулировать один ожидаемый результат;
- предложить 2–3 реальных варианта для архитектурной развилки;
- сравнить объём изменений, риск миграции, сценарии отказа, способ отката и
  доказательства;
- рекомендовать один вариант;
- подготовить контракт среза.

Для механической задачи не требуется искусственно придумывать альтернативы.
Архитектор должен объяснить, почему реальной развилки нет.

Архитектор не пишет рабочий код.

`high` или `xhigh` допустимы только для сложной архитектуры, анализа безопасности,
сценариев отказа или итоговой проверки, когда дополнительный расход оправдан.
`max` не используется по умолчанию.

### 8.2 Исполнитель: GPT-5.5 xhigh

Режим: отдельный запуск после одобрения контракта.

Обязан:

- реализовать только утверждённый контракт задачи;
- не менять архитектуру по ходу работы;
- не выходить за список разрешённых файлов и лимит изменений;
- запускать предусмотренные проверки;
- остановиться после `technical_done`;
- записать доказательства и непроверенные области.

Если во время реализации появляется новая архитектурная развилка, Исполнитель
не выбирает её. Он останавливается и возвращает задачу Архитектору.

### 8.3 Исследователь кода (Code Scout): GPT-5.4 high

Режим: свежий запуск только для чтения после `technical_done`.

Ищет по коду то, что могли пропустить Архитектор и Исполнитель:

- все места вызова и использования, а также скрытую область влияния;
- устаревшие, дублирующие и альтернативные пути выполнения;
- ошибки идемпотентности, повторов, конкурентного выполнения и обработки
  отказов;
- слабые, ложно-зелёные или отсутствующие тесты;
- нарушения границ модулей и публичных контрактов;
- мёртвый код, несовместимости типов и конфликты миграций;
- утечки персональных данных или секретов и небезопасное журналирование.

Каждая находка содержит:

- файл и точную локацию;
- наблюдаемое доказательство;
- последствие;
- способ воспроизведения или проверки;
- уровень уверенности и неизвестные обстоятельства.

Исследователь кода не редактирует код. Он может записать находки только в
назначенный отчёт проверки или документ задачи, не принимает архитектурные
решения и не объявляет срез принятым.

### 8.4 Независимый проверяющий (Reviewer): GPT-5.6 Sol

Режим: свежий запуск только для чтения.

Вход:

- одобренный контракт задачи;
- исходный и итоговый SHA;
- набор изменений;
- действующие документы и ADR;
- доказательства выполненных проверок;
- отчёт Исследователя кода.

Проверяющий сначала делает собственный проход, затем проверяет находки
Исследователя кода. Отчёты Исполнителя и Исследователя кода считаются
утверждениями, а не доказательствами.

Проверяющий обязан составить карту затронутых областей:

- модули, интерфейсы и зависимости;
- БД, миграции и владение состоянием;
- обычное поведение и сценарии отказа;
- промпты, инструменты, настройки моделей и правила;
- приватность, проверка права на отправку и управление со стороны менеджера;
- тесты, наборы оценки и наблюдаемость;
- развёртывание, откат и отчёты выпуска;
- потребители в других репозиториях.

Вердикт:

- `accept` — принять технический результат;
- `needs_fix` — нужны исправления в прежней области работы;
- `needs_evidence` — не хватает доказательств;
- `needs_redesign` — нужно заново выбрать решение;
- `needs_human_decision` — требуется решение владельца.

Проверяющий не исправляет код.

### 8.5 Исправление (Repair): GPT-5.5 xhigh

Исправление является новым запуском внутри того же идентификатора среза.

Оно устраняет только подтверждённые находки внутри прежней области работы. Если
находка требует расширения области, создаётся новое предложение, а текущий
запуск останавливается.

После исправления Исследователь кода и Проверяющий повторяют работу в объёме,
соответствующем изменившейся области влияния.

По умолчанию разрешён один запуск исправления. Второй требует нового одобрения и
обновлённого лимита изменений. Повтор той же категории дефекта после исправления
переводит срез в `needs_redesign` или `needs_human_decision`.

### 8.6 Учитель (Teacher): GPT-5.6 Sol

Учитель запускается отдельно в режиме только чтения после вердикта `accept`.

Он получает контракт задачи, принятый набор изменений, вердикт Проверяющего и
контрольный список понимания. Учитель не меняет код, не переоткрывает принятую
проверку без нового доказательства и не начинает следующий срез.

## 9. Контракт самостоятельной постановки задачи

Codex создаёт срез в следующем порядке:

1. **Результат:** один видимый итог.
2. **Источники истины:** код, спецификация, ADR, задача и доказательства.
3. **Исходное состояние:** SHA, состояние рабочей копии и известные
   противоречия.
4. **Критерии успеха:** что должно стать истинным.
5. **Область работы:** разрешённые изменения.
6. **Вне области:** явные соседние задачи.
7. **Ожидаемые файлы и модули:** точная область касания.
8. **Лимит изменений:** количество файлов и строк рабочего кода.
9. **Разрешённые действия:** чтение, запись, тесты и прототипы.
10. **Проверки:** целевые тесты, проверка типов, сборка, наборы оценки и
    минимальная сквозная проверка.
11. **Последовательность ролей:** модель для каждого отдельного запуска.
12. **Доказательства:** обязательные материалы и проверки.
13. **Остановка и передача решения:** когда остановиться или обратиться к
    владельцу.
14. **Контрольный список понимания:** что владелец должен понять.

Контракт задачи сначала получает одобрение. Реализация не начинается в том же
сообщении, где впервые предложена новая архитектурная развилка.

## 10. Область работы и лимит изменений

Перед реализацией фиксируются:

- точный список ожидаемых файлов рабочего кода;
- допустимые пути для тестов, документов и проверочного стенда;
- максимальное число затрагиваемых файлов рабочего кода;
- ориентир добавленных или изменённых строк рабочего кода;
- ожидаемая область влияния.

Обязательная остановка:

- понадобился неутверждённый модуль или файл;
- объём изменений рабочего кода превысил ориентир более чем на 50%;
- возникло незаявленное изменение БД, публичного контракта, промпта, инструмента,
  настройки модели, правил приватности, проверки права на отправку или
  потребителя из другого репозитория;
- новая архитектурная развилка появилась во время реализации;
- тесты показывают необходимость соседнего рефакторинга;
- критерии успеха уже доказаны.

Порог количества строк не заменяет инженерное решение. Большое удаление,
созданные генератором файлы или механическое перемещение оцениваются по
затронутым областям и риску, а не только по итоговой разнице числа строк.

## 11. Правила минимальности

- Исправление ошибки начинается с теста, воспроизводящего дефект.
- Высокорисковая гипотеза сначала проверяется изолированным одноразовым
  прототипом или проверочным стендом.
- Одноразовый код не попадает в рабочий контур без отдельного решения.
- Большой проверочный стенд не оправдывает большой объём изменений рабочего
  кода.
- Предположительные абстракции, широкая чистка и массовые переименования
  «заодно» запрещены.
- Новая зависимость требует отдельного обоснования и одобрения, если её не было
  в контракте задачи.
- После достижения критериев успеха дополнительная полировка запрещена.
- Завершённый вызов инструмента не повторяется без нового основания.
- При пустом или неполном результате поиска разрешены один-два осмысленных
  запасных способа поиска, после чего фиксируется нехватка доказательств.
- Количество повторов временно неудачной операции ограничивается контрактом
  задачи.

## 12. Проверки и доказательства

До `technical_done` обязательны:

- целевые тесты изменённого поведения;
- проверка типов и запуск линтера, если они применимы;
- сборка затронутого пакета;
- применимые тесты архитектурных границ;
- применимые локальные наборы оценки;
- минимальная сквозная проверка, если она не требует внешнего или платного
  действия;
- `git diff --check`;
- полный `git diff --stat`;
- полный список затронутых файлов;
- исходный и итоговый SHA;
- список непроверенных областей;
- способ отката или безопасного отказа от изменения.

Платная оценка на живой модели, записи в тестовую или рабочую среду, миграции,
изменения секретов или настроек и другие действия с обязательной проверкой всё
ещё требуют отдельного одобрения владельца.

Невозможность запустить проверку не превращается в успешный результат. Статус
становится `needs_evidence`.

## 13. Проверка понимания через обратное объяснение

После `accept` отдельно запускается Учитель. Код больше не меняется.

Живой контрольный список Markdown хранится в документе текущего среза и
содержит:

- проблема и причина;
- реальные развилки;
- выбранное решение и причина выбора;
- ключевые проектные решения;
- существенные краевые случаи и сценарии отказа;
- доказательства и способы проверки;
- более широкий контекст и влияние на следующие части системы;
- граница следующего среза.

Протокол:

1. Сначала попросить владельца своими словами пересказать понимание среза.
2. Найти пробелы по контрольному списку.
3. Задавать ровно один вопрос за раз.
4. Использовать открытые вопросы или варианты ответа.
5. Не раскрывать правильный ответ до ответа владельца.
6. При необходимости показать код, тест, трассировку или порядок работы с
   отладчиком.
7. Объяснять «почему», затем проверять «что» и «как».
8. Разрешить команды `проще`, `как для пятилетнего`, `как для
   четырнадцатилетнего`, `как для стажёра`, `пауза`, `дай итог` и `дай recap`.

`AskUserQuestion` используется, когда он доступен в текущем режиме. В остальных
режимах задаётся один обычный вопрос в чате.

### 13.1 Измеримые критерии завершения

`understanding_verified` возможен, только если владелец на деле:

1. объяснил причину проблемы и ключевую развилку;
2. обосновал выбранное решение против главной альтернативы;
3. разобрал минимум один существенный краевой случай или сценарий отказа;
4. назвал доказательства и сигнал, который опроверг бы корректность;
5. объяснил влияние на следующие части системы и границу следующего среза.

Модель не использует субъективное «я убедилась» как единственный критерий.

Если механизм долгоживущей цели доступен и явно включён для обратного объяснения,
цель остаётся активной до выполнения критериев завершения. Пользователь может
поставить сессию на паузу, но следующий срез остаётся заблокированным.

Контрольный список понимания отражает состояние учебной сессии, а не является
источником истины о продукте. Подробные заметки о знаниях владельца создаются
только после его явной просьбы зафиксировать конкретное знание.

## 14. Поведение при проблемах

- Конфликт источников истины → `needs_human_decision` или сверка исходного
  состояния.
- Не хватает доказательств → `needs_evidence`.
- Требуется расширить область работы → остановка и новое предложение.
- Находка внутри прежней области работы → запуск исправления.
- Находка вне прежней области работы → кандидат на следующий срез.
- Ошибка архитектуры → `needs_redesign`, без исправления по месту.
- Нужная модель недоступна → `needs_human_decision`, без автоматической подмены.
- Пользователь поставил обучение на паузу → `teaching_paused`, следующий срез
  заблокирован.
- Критерии понимания выполнены → `understanding_verified`, затем остановка.

## 15. Отклонённые альтернативы

### Один большой `AGENTS.md`

Отклонён: автоматически применяется, но раздувает постоянный контекст и
увеличивает риск повторов и конфликтов.

### Только `docs/AGENT_WORKFLOW.md`

Отклонён: меньше файлов, но Codex не обязан автоматически загрузить его до
начала работы.

### Субагенты, Terra и Ultra

Отклонены решением владельца. Работа идёт последовательными свежими запусками с
явным разделением ролей.

### Один агент реализует и принимает собственную работу

Отклонён: самопроверка полезна, но не заменяет независимую проверку свежим
запуском.

### Автономно выполнить весь план рефакторинга

Отклонён: разрешён только один срез, затем независимая проверка, обратное
объяснение и остановка.

### Бесконечное обучение по субъективному ощущению модели

Отклонён: сохранена строгая проверка понимания, но конец определяется
наблюдаемыми критериями. Пауза не равна принятию.

## 16. Критерии готовности комплекта правил

Комплект правил считается готовым, если:

- корневой `AGENTS.md` короткий и автоматически направляет к подробным
  инструкциям;
- рабочее руководство содержит только недублирующиеся правила;
- шаблон среза делает обязательными область работы, лимиты, роли, доказательства
  и проверку понимания;
- ни один файл не разрешает субагентов, Terra или Ultra;
- один запуск не совмещает реализацию и приёмочную проверку;
- следующий срез нельзя начать до `understanding_verified`;
- исторические документы не могут молча переопределить принятый источник истины;
- существуют проверяемые сценарии для расширения области, превышения лимита,
  нехватки доказательств, находки Исследователя кода, исправления и паузы
  обучения;
- текущий рабочий код, промпты, инструменты, настройки моделей и состояние
  системы не меняются.

## 17. Вне области этой спецификации

- Реализация будущей архитектуры AI-слоя.
- Исправление текущего исходного состояния Mastra/live-v2.
- Изменение промптов, правил, инструментов или настроек моделей рабочего
  AI-контура.
- Создание миграций БД.
- Запуск платной оценки на живой модели.
- Действия в тестовой или рабочей среде.
- Автоматическая смена модели внутри запуска.
- Субагенты, Terra и Ultra.

## 18. Текущее состояние и следующий шаг

Комплект правил реализован в `AGENTS.md`, рабочем руководстве и шаблоне среза.
Он не меняет рабочий AI-контур.

Когда владелец предоставит будущую схему AI-слоя:

1. создать отдельный документ задачи по шаблону среза;
2. первым свежим запуском GPT-5.6 Sol выполнить роль Архитектора;
3. сверить схему с фактическим исходным состоянием репозитория;
4. получить одобрение одного узкого среза;
5. только затем передать его Исполнителю GPT-5.5 `xhigh`.

Фактическая сверка AI-слоя и новая архитектура остаются отдельными будущими
срезами.
