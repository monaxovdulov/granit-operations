# Правила работы Codex в `granit-operations`

Этот файл загружается автоматически. Держи его коротким: подробности находятся
в документах по ссылкам ниже.

## Общий порядок

Перед изменениями прочитай:

1. `README.md`;
2. `docs/source-of-truth.md`;
3. `docs/AGENT_WORKFLOW.md`;
4. документ текущей задачи;
5. относящиеся к задаче ADR и архитектурные документы.

Сохраняй чужие незавершённые изменения. Не считай исторический план или старый
отчёт проверки действующим источником истины без сверки с текущим SHA, кодом и
принятыми ADR.

## Рефакторинг AI-слоя

Для проектирования, реализации или проверки рефакторинга AI-слоя обязательно
прочитай:

- `docs/AI_AGENT_REFACTOR_PLAYBOOK_RU.md`;
- текущую компактную карточку среза по
  `docs/tasks/AI_REFACTOR_SLICE_TEMPLATE_RU.md`;
- `docs/architecture/AI_REFACTOR_MINIMAL_GOAL_GOVERNANCE_RU.md` при изменении
  самого процесса.

Весь утверждённый roadmap может выполняться внутри одной долгоживущей Goal.
Goal не отменяет границы репозитория, внешние разрешения и независимую проверку.

## Неподвижные правила

- Одновременно изменяется только один срез с одним видимым результатом.
- После `accept` Goal автоматически переходит к следующему заранее указанному
  срезу; отдельное поручение владельца не требуется.
- Субагенты, Multi-agent, Terra и Ultra запрещены.
- Автор изменений не принимает собственную работу.
- Обязательны две роли: Исполнитель и свежий независимый Проверяющий.
  Проверяющий включает Code Scout: callers, failure paths, concurrency,
  migrations, privacy и false-green tests.
- Архитектор запускается только при новой существенной развилке; обычное
  исправление замечаний остаётся у Исполнителя внутри прежнего среза.
- Соседняя работа записывается как кандидат следующего среза и не выполняется.
- После достижения критериев успеха дополнительная полировка запрещена.
- Каждый срез имеет отдельный diff/commit/PR или другой явно отделимый набор
  изменений. Commit, push, PR и deploy выполняются только когда поручены.
- Учитель и `understanding_verified` нужны один раз после технического
  завершения всей Goal или явно выбранной крупной вехи.

## Четыре стоп-гейта

Немедленно остановись для решения владельца, если требуется:

1. новая архитектурная развилка, меняющая утверждённый roadmap или ownership;
2. миграция/схема БД либо изменение публичного контракта;
3. изменение промпта, инструмента, модели, AI-policy, privacy, send gate или
   manager takeover;
4. deploy, секреты/runtime-конфигурация, платный внешний вызов, другой
   репозиторий или иное внешнее воздействие.

Если действие уже точно описано и явно одобрено в текущей Goal/карточке, заново
спрашивать не нужно. Нужная модель — рекомендация, а не стоп-гейт: зафиксируй
фактическую модель и продолжай, если владелец не потребовал точную.

## До записи рабочего кода

В компактной карточке среза зафиксируй:

- один результат;
- исходный SHA и источник истины;
- область и явные исключения;
- проверки успеха;
- непроверенные риски и откат.

Точный список файлов и жёсткий лимит строк обязательны только для
высокорискового среза. В остальных случаях область задаётся модулями, а размер
diff является ориентиром: существенное расширение объясняется в карточке и
проверяется Reviewer.

## Перед завершением технической роли

Зафиксируй:

- исходный и итоговый SHA;
- полный список затронутых файлов и `git diff --stat`;
- область прямого и косвенного влияния;
- выполненные тесты, проверку типов, сборку и применимые оценки;
- непроверенные области;
- способ отката или безопасного отказа от изменения.

Невыполненная обязательная проверка означает `needs_evidence`, а не успешный
результат. После независимого `accept` обнови карточку и продолжай следующую
задачу Goal автоматически.
